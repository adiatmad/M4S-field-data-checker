## Findings

### 1. [HIGH] The UI has no declared design direction and is not marked as a draft

- **Rule:** [R-37, Design Direction Required](https://github.com/miqdadbadjuber/anti-slop/blob/main/antislop.md#r-37--design-direction-required)
- **Evidence:** The repository tree has no `DESIGN.md` or project entry file routing agents to Anti-Slop. The unified app selects a wide Streamlit layout and workflow at [`m4s_app.py:1103-1108`](https://github.com/adiatmad/M4S-field-data-checker/blob/main/m4s_app.py#L1103-L1108), but no design brief or ENERGY / RHYTHM / MOTION dials are recorded.
- **Why it matters:** The core forbids silently falling back to a neutral default when design direction is absent. This does not mean the app needs flashy visuals; a restrained, field-work-first interface could be the right choice, but that choice needs owner direction.
- **Recommended fix after approval:** Ask one decisive question about the intended UI identity and audience, record the owner's answer, and then audit the UI against that direction. Do not invent a palette or redesign before that answer. If the owner chooses to defer direction, follow the core's explicit draft-without-direction path rather than presenting a redesigned UI as finished.

### 2. [HIGH] There is no recorded UI click-through verification

- **Rule:** [R-35, Verify Before You Deliver](https://github.com/miqdadbadjuber/anti-slop/blob/main/antislop.md#r-35--verify-before-you-deliver)
- **Evidence:** [`README.md:63`](https://github.com/adiatmad/M4S-field-data-checker/blob/main/README.md#L63) explicitly says Streamlit UI interactions were not separately exercised. The workflow [`.github/workflows/generic-csv-tests.yml`](https://github.com/adiatmad/M4S-field-data-checker/blob/main/.github/workflows/generic-csv-tests.yml) installs dependencies, compiles Python files, and runs pytest; it does not launch either app or record a control-by-control click-through.
- **Why it matters:** Compilation and unit tests provide useful evidence, but they do not establish that file upload, filtering, tabs, downloads, loading, and failure states work in the actual UI. The core requires the click-through evidence to be recorded rather than inferred from code.
- **Recommended fix after approval:** Add a bounded, reproducible UI verification procedure or suitable automated UI checks, and record results for both entry points, including valid and invalid uploads, empty findings, filters, tabs, downloads, keyboard use, and narrow viewport behavior. Do not claim a pass for paths that were not exercised.

### 3. [HIGH] The M4S success message overstates what the checks establish

- **Rule:** [R-38, Real Content or Honest Placeholder](https://github.com/miqdadbadjuber/anti-slop/blob/main/antislop.md#r-38--real-content-or-honest-placeholder) and Craftsmanship Standard C-5 (Evidence Over Claims).
- **Evidence:** [`m4s_app.py:1179`](https://github.com/adiatmad/M4S-field-data-checker/blob/main/m4s_app.py#L1179) displays: “No QA flags triggered! All data looks clean.” The generic CSV workflow uses narrower wording at [`m4s_app.py:1091`](https://github.com/adiatmad/M4S-field-data-checker/blob/main/m4s_app.py#L1091): “No findings from the enabled generic checks.” The README also says a clean result does not certify the entire survey as valid.
- **Why it matters:** No triggered flags means only that the configured rules found nothing. It does not establish that all records are correct, the survey form was fully validated, or every ecological rule was checked.
- **Recommended fix after approval:** Replace the broad success claim with wording scoped to the checks actually run. Preserve the domain rules and their existing thresholds; this finding concerns the claim shown to the user, not the scientific rules.

### 4. [HIGH] The M4S UI does not provide an app-controlled error state for the full pipeline

- **Rule:** [R-27, UI States](https://github.com/miqdadbadjuber/anti-slop/blob/main/antislop.md#r-27--ui-states), plus C-4 (Resilience).
- **Evidence:** [`m4s_app.py:1118-1139`](https://github.com/adiatmad/M4S-field-data-checker/blob/main/m4s_app.py#L1118-L1139) catches `ValueError` around `load_data`, but calls `standardize`, `validate`, `add_qa_columns`, and `correct` after that handler without an equivalent app-level failure boundary.
- **Why it matters:** The UI has an upload-empty state and a loading indicator, and it handles a known loading error. An unexpected failure in a later stage can bypass the intended user-facing error message and interrupt the workflow without a clear, actionable explanation.
- **Recommended fix after approval:** Add a narrow failure boundary around the M4S processing stages that reports the failed stage safely, stops the run, and never presents partial results as complete. Preserve the original uploaded data and existing correction-log behavior. Do not expose raw exception details or silently convert failures into clean results.

### 5. [HIGH] Em dashes appear in user-facing copy and generated output

- **Rule:** [R-02, Copywriting](https://github.com/miqdadbadjuber/anti-slop/blob/main/antislop.md#r-02--copywriting).
- **Evidence:** Examples include GPS findings at [`m4s_app.py:261-268`](https://github.com/adiatmad/M4S-field-data-checker/blob/main/m4s_app.py#L261-L268), the UI heading at [`m4s_app.py:1150`](https://github.com/adiatmad/M4S-field-data-checker/blob/main/m4s_app.py#L1150), and the generated report heading at [`m4s_app.py:668`](https://github.com/adiatmad/M4S-field-data-checker/blob/main/m4s_app.py#L668). The README also uses em dashes as separators.
- **Why it matters:** R-02 forbids the em-dash character in text the agent writes. The core's scope is agent-authored text, so the original authorship of inherited copy must not be guessed.
- **Recommended fix after approval:** Review and rewrite the affected copy using commas, periods, colons, or parentheses where appropriate. Keep the meaning and technical facts unchanged. Do not perform a blind global replacement that changes scientific messages, identifiers, or unrelated source text.

### 6. [MEDIUM] Literal emoji are used as decoration throughout the M4S UI

- **Rule:** Purpose-Gate [R-04, Icons](https://github.com/miqdadbadjuber/anti-slop/blob/main/antislop.md#r-04--icons), plus the Anti-Slop UI skill section “Emoji as Decoration”.
- **Evidence:** Emoji appear in the page title and metric labels at [`m4s_app.py:1103-1108`](https://github.com/adiatmad/M4S-field-data-checker/blob/main/m4s_app.py#L1103-L1108), section heading at [`m4s_app.py:1150`](https://github.com/adiatmad/M4S-field-data-checker/blob/main/m4s_app.py#L1150), success state at [`m4s_app.py:1179`](https://github.com/adiatmad/M4S-field-data-checker/blob/main/m4s_app.py#L1179), download controls, and tab labels at [`m4s_app.py:1267-1268`](https://github.com/adiatmad/M4S-field-data-checker/blob/main/m4s_app.py#L1267-L1268). No UI rationale documents why these marks are needed.
- **Why it matters:** The UI skill says to remove emoji from UI text and use a relevant icon only when it adds meaning and its purpose is recorded. Repeated emoji compete with operational labels and give unrelated controls the same visual emphasis.
- **Recommended fix after approval:** Remove decorative emoji from headings, metrics, buttons, and tab labels. Keep a page icon only if the owner confirms it serves a real recognition purpose; use no replacement icon where text is clearer. Do not add a new visual system without resolving finding 1.

### 7. [LOW] Decorative section banners and workflow-narration comments add noise

- **Rule:** Quality Lock [R-31, Every Decision Must Have a Reason](https://github.com/miqdadbadjuber/anti-slop/blob/main/antislop.md#r-31--every-decision-must-have-a-reason-write-it-down), applied through the [Anti-Slop code-comment skill](https://github.com/miqdadbadjuber/anti-slop/blob/main/skills/antislop-code/SKILL.md).
- **Evidence:** Repeated-character banners and stage labels appear in [`m4s_app.py:83`](https://github.com/adiatmad/M4S-field-data-checker/blob/main/m4s_app.py#L83), [`m4s_app.py:190`](https://github.com/adiatmad/M4S-field-data-checker/blob/main/m4s_app.py#L190), [`m4s_app.py:232`](https://github.com/adiatmad/M4S-field-data-checker/blob/main/m4s_app.py#L232), and the parallel CLI implementation, for example [`m4s_seagrass_qa.py:64`](https://github.com/adiatmad/M4S-field-data-checker/blob/main/m4s_seagrass_qa.py#L64). Comments such as “Show count” and “Apply filters” narrate operations already visible in the following code.
- **Why it matters:** The code-comment skill specifically identifies decorative separators, empty labels, and workflow narration as noise. It also explicitly says not to change executable code, formatting, or logic during comment cleanup.
- **Recommended fix after approval:** Remove or simplify only comments that add no information. Preserve comments explaining domain assumptions, scientific rules, safety/privacy boundaries, edge cases, and non-obvious behavior. Keep this as a comment-only change and verify the diff contains no executable-code changes.
